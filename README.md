# Доказательный RAG по ТФКП

## Aрхитектура

Пайплайн: PDF -> параграфы -> корпус -> BM25-индекс -> ответы LLM -> эвалюция.

**Индекс.** BM25 по блокам корпуса (`block_id, page, section, text`).
Токенизация общая для индекса и запроса (`scripts/tokenizer.py`):
сохраняются числа-ссылки (`2.1`, `1.2.3`), идентификаторы (`u_x`, `x^2`)
и математические символы. Заголовок секции индексируется с весом 2
относительно основного текста.

**Пайплайн ответа.**

Довольно стандартно

1. Запрос в BM25 = вопрос + тексты вариантов ответа.
2. Top-k блоков идут в prompt как фрагменты с `block_id`.
3. Один вызов LLM возвращает JSON: выбранные варианты, `abstain`,
   `rationale`, `citations`.
4. Валидация: `citations` как множество блоков из шага 2; `abstain=false`
   требует непустые `answer_ids` и `citations`. При ошибке - один retry (кроме оговоренных исклбчений из задания).

**Аблации.**

* `full` (полный пайплайн),
* `rag_single` (RAG с одним поиском и одним вызовом LLM),
* `no_context` (модель без контекста),
* `ablation_no_rerank` (BM25 выбирает top-k, блоки упорядочены по позиции
в корпусе.),
`ablation_top1`.

**Оценка.** оценка взята из спецификации, однако `baseline` не был приведен вместе с заданием или пояснен в надлежащим виде. Считатеся как `answer_accuracy` (точное совпадение вариантов, отказ на
недостаточности источника) и `Q` (среднее по категориям с учётом F1
цитат). Efficiency и Итог считаются по стоимости из trace и входят в лог.

## Установка и запуск

```sh
pip install -r -requrements
```

### Сборка индекса

```sh
python scripts/extract_markdown.py \
    --pdf=data/textbook.pdf \
    --paragraphs=data/paragraphs.jsonl \
    --markdown=data/extracted.md

python scripts/build_corpus.py \
    --input=data/paragraphs.jsonl \
    --output=data/corpus.jsonl

python scripts/generate_gold.py \
    --pairs=data/pairs.jsonl \
    --corpus=data/corpus.jsonl

python build_index.py \
    --config=config.json \
    --corpus=data/corpus.jsonl \
    --output=index
```

(`extracted.md` - отладочный артефакт, остальные пайплайны его не читают).
После изменения `scripts/tokenizer.py` индекс нужно пересобрать.

### Predict

```sh
python predict.py \
    --index ./index \
    --questions ./data/dev_questions.jsonl \
    --output ./dev_answers.jsonl \
    --trace ./dev_trace.jsonl \
    --config ./config.json \
    --runtime ./runtime.json \
    --experiment-name `full` (полный пайплайн)
```

Флаг `--experiment-name` переключает эксперимент: `no_context` - без retrieval, ответ из памяти, `rag_single` - без retry, etc..

Пример полного прогон по всем экспериментам в ноутбуке `experiments.py`.

Для сборки конечного артифакта в виде `experiments.csv`:

```
python evaluate.py \
    --gold ./data/dev_gold.jsonl \
    --answers-dir . \
    --traces-dir . \
    --csv ./experiments.csv
```

Запуск проводился на Google Cloab с помощью директории проекта. Пайплайн целиком можно посмотреть в ноутбуке `experiments.ipynb`

## Ресурсы

**Файлы.**

- `data/textbook.pdf` - исходник с лекциями.
- `data/paragraphs.jsonl` - параграфы/заголовки с номером страницы.
- `data/corpus.jsonl` - блоки для индекса.
- `data/pairs.jsonl` - вопросы, эталоны, `reference_pages`, `source_locator`.
- `data/dev_gold.jsonl`, `data/dev_questions.jsonl` - соответсвующие референсы, выход `generate_gold.py`.
- `index/` - диреткория для зранения состояния индекса (`documents.jsonl`, `bm25.pkl`, `manifest.json`).


**Вычисления.**

1. Сборка индекса: CPU, < секунда.

2. Predict: GPU для LLM, CPU для BM25. Кол-во вызовов LLM на вопрос -
    преимущественно 1 за исключением ошибок.

    Запуск на бесплатных машинах Colab с T4 занимает ~2 мин на набор из 15 вопросов.

3. Evaluation: читый Python на CPU.


Лимиты на вопрос (LLM): 4 вызова, 16 384 входных токенов,
4 096 выходных, 8 192 на один запрос. (Берутся из спецификации.) Trace фиксирует расход;
превышение обнуляет эффективность прогона.

**Конфиги**

1. `config.json` - параметры индекса (BM25 k1/b, токенизация). Замораживается после сборки индекса для сверки версий.

2. `runtime.json` - то, что публикуется: `top_k`, `temperature`, `max_tokens`, `model.revision`, budget, etc..

## Результаты

На 15 вопросах `answer_accuracy` шагает по 0.067 (1/15). Почти все расхождения между экспериментами лежат внутри одного вопроса (0.7333 vs 0.6667).

Из цифр можно подтвердить, что

* `insufficient` = 1.00 везде. (Стабильный, воспроизводимый сигнал.) Модель уверенно отказывается на всех вопросах недостаточности источника - это стабильный, воспроизводимый сигнал, не связанный с retrieval.
* качество на задачах `synthesis` заметно падает при top-1: 0.84 → 0.625. (Качественно ожидаемое отличие.) Вероятно вопросы этого типа требуют нескольких фрагментов, которые соовтественно не попдают top-1 их не даёт.
* Расход токенов и retry работают корректно. Для всего пайплайна `mean_cost` вырос на ~160 единиц относительно `rag_single` (стоимость одного retry). Трейс также ведётся правильно.
* Latency реагирует на размер контекста. top-5 ~ 12 с, top-1 ~ 8 с, no_context ~ 7.5 с - согласуется с объёмом входных токенов.
* no_context отстаёт всего на один вопрос. Так что RAG улучшил качество ответа, но повысил стоимость.
- Задачи `application` самые сложные для модели во всех пяти экспериментах.Возможно проблема не в поиске, а в модели, промпте или в самих эталонах этой категории. Стоит открыть три вопроса и посмотреть, что модель отвечает.

### Итог

Результаты согласованы, но возможно `dev`-набор слишком мал для выводов

Возможно стоит расширить лист вопросов до нескольких десятков. Тогда `full` vs `rag_single` vs `no_context` могут начать различаться статистически. Пока что выводы об эффективности retry и top-k могут быть в пределах погрешности. 

Стоит попробовать top-3. Возможно, top-5 "размывает" промпт лишним контекстом для вопросов про условия теорем. Top-3 - тогда компромисс между top-1 и top-5.

Разобрать `application`, так как основные грабли для модели.
